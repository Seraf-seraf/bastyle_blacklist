# Архитектура Bastyle Blacklist

Документ фиксирует архитектуру приложения, текущие границы модулей и
архитектурные ограничения масштабирования после перехода с локального SQLite на
PostgreSQL.

## Назначение

Bastyle Blacklist - Telegram-бот для автоматической модерации медиа в групповых
чатах. Администратор отвечает командой `/ban` на нежелательное медиа, бот
сохраняет признаки этого медиа в черный список, удаляет исходное сообщение и
затем автоматически удаляет повторные или похожие отправки.

Поддерживаемые виды сопоставления:

- точное совпадение по Telegram `file_unique_id`;
- перцептивный хеш изображений для фото и статичных стикеров;
- хеширование кадров для Telegram-анимаций и WebM-видеостикеров;
- векторное сопоставление на основе ИИ через отдельный сервис Python/FastAPI и
  локальный индекс FAISS HNSW.

Обычные Telegram-видео и документы вне текущей зоны ответственности.

## Статус реализации

Текущий код уже использует PostgreSQL как хранилище черного списка, артефактов
сопоставителей, ИИ-векторных данных, журнала исходящих событий Watermill и
контрольных точек индексов. Локальные Go-индексы exact/imagehash/videolike и
локальный индекс FAISS остаются производными проекциями времени выполнения.

Важно отделять текущий код от инфраструктурной целевой схемы:

- в конфиге и коде PostgreSQL обязателен;
- текущий `infra/docker-compose.yaml` поднимает Go-бот, ИИ-сервис
  сопоставления и RabbitMQ, но не поднимает сервис PostgreSQL;
- PostgreSQL для локального Docker Compose или промышленного окружения должен
  быть предоставлен отдельно до закрытия этапа обновления Compose;
- SQLite на каждую реплику не входит в целевую схему и не должен возвращаться в
  рабочий путь выполнения.

## Целевая схема

```text
Telegram-группа / пользователь
  -> Telegram Bot API
  -> API-шлюз / Nginx / маршрутизация платформы
  -> реплика Bastyle Bot N
      -> go-bot
          -> сервис модерации
          -> оркестратор блокировок
          -> основной узел PostgreSQL
              -> media_ban
              -> blocked_exact
              -> blocked_image / blocked_image_hash
              -> blocked_video_like / blocked_video_like_frame_hash
              -> ai_vector_ban / ai_vector_frame
              -> ai_vector_index_state
              -> watermill_outbox_events
              -> watermill_offsets_outbox_events
              -> index_checkpoints
          -> локальная карта exact
          -> локальный imagehash LinearIndex
          -> локальный videolike LinearIndex
          -> публикация и потребление RabbitMQ
          -> HTTP-клиент к ИИ-сервису сопоставления
      -> ai-matcher FastAPI
          -> основной узел PostgreSQL
          -> модель построения векторных представлений изображений на Transformers
          -> локальный индекс FAISS HNSW

основной узел PostgreSQL
  -> резервные реплики PostgreSQL только для чтения

обменник RabbitMQ типа topic bastyle.events
  -> устойчивые quorum-очереди для каждой реплики
```

## Источник истины

Источник истины:

- основной узел PostgreSQL.

Производные данные:

- локальная карта exact в Go-боте;
- локальные imagehash и videolike `LinearIndex` в Go-боте;
- локальный индекс FAISS HNSW в ИИ-сервисе сопоставления;
- сообщения RabbitMQ;
- резервные реплики PostgreSQL только для чтения.

RabbitMQ является быстрым каналом сигналов. Долговременная история событий для
догоняющей синхронизации хранится в журнале исходящих событий PostgreSQL.
Локальный индекс не
считается источником истины и должен быть полностью восстанавливаем из
активных записей блокировок PostgreSQL.

## Архитектурные ограничения

- Все операции записи приложения идут в основной узел PostgreSQL.
- Репликация PostgreSQL не является многоосновной схемой.
- Резервные реплики PostgreSQL остаются доступными только для чтения до
  переключения основного узла.
- Критичные для модерации чтения на текущем этапе идут в основной узел, чтобы
  не зависеть от отставания репликации.
- Локальные индексы являются кешем/проекцией и должны безопасно переживать
  пересборку.
- Применение событий индексов должно быть идемпотентным: новая реплика может
  построить индекс из БД и затем увидеть старое событие исходящего журнала.
- Полезная нагрузка RabbitMQ не является единственным источником истины для
  синхронизации индексов. Потребитель после сигнала догоняет события из
  исходящего журнала PostgreSQL по контрольной точке.
- Для новых путей массового сохранения нельзя делать `INSERT` в цикле, если
  данные можно собрать и записать одной пакетной операцией.
- Запросы к БД должны избегать N+1: загрузка активных артефактов и векторов
  выполняется соединениями `JOIN` и группировкой на стороне приложения.

## Go-Бот

Go-сервис находится в `services/bot`.

Основные слои:

- `cmd/main.go` - точка сборки приложения, длинный опрос Telegram, воркеры,
  проверка состояния, метрики, публикатор исходящих событий и запуск
  потребителя индексных событий;
- `internal/domain` - доменные структуры Telegram-сообщений, контента и
  медиакадров;
- `internal/app/ports` - интерфейсы для модерации, проверки администратора,
  действий с сообщениями, загрузки/извлечения медиа, исходящих событий и
  синхронизации индексов;
- `internal/app/moderation` - сценарий обработки сообщений и команд;
- `internal/adapters/matching/orchestrator` - транзакционный оркестратор
  `/ban`;
- `internal/adapters/matching/*` - адаптеры сопоставителей exact, imagehash,
  videolike и ИИ-векторного сопоставителя;
- `internal/adapters/database/postgres` - пул PostgreSQL и помощник транзакций;
- `internal/adapters/outbox/postgres` - запись и чтение исходящего журнала
  Watermill, а также хранилище данных для метрик;
- `internal/app/indexsync` - догоняющая синхронизация локальных индексов по
  контрольным точкам;
- `internal/adapters/messaging/rabbitmq` - публикатор Watermill AMQP и
  подписчик индексных событий на каждую реплику;
- `internal/adapters/telegram` - действия Telegram API, проверка
  администратора, загрузчик файлов и преобразователь сообщений;
- `internal/adapters/media` - ограниченный декодер изображений и извлекатель
  кадров FFmpeg.

### Запуск Go-бота

1. Загружается YAML-конфиг со строгой проверкой полей через `KnownFields`.
2. Открывается пул PostgreSQL.
3. Создается клиент Telegram Bot API.
4. Создаются сопоставители на PostgreSQL:
   - exact загружает активные `blocked_exact` в карту;
   - imagehash загружает активные хеши в `LinearIndex`;
   - videolike загружает активные хеши кадров в `LinearIndex`;
   - ИИ-векторный сопоставитель, если включен, создает HTTP-клиент к
     ИИ-сервису.
5. Собирается `BlockOrchestrator`.
6. Поднимаются HTTP-сервер проверки состояния и сервер метрик, если они
   включены.
7. Если включен публикатор исходящих событий, запускается пересылка Watermill из
   исходящего журнала PostgreSQL в RabbitMQ.
8. Если включены `consumers.index_events`, создается синхронизатор, выполняется
   догоняющая синхронизация локальных индексов по исходящему журналу PostgreSQL
   при старте, затем запускается RabbitMQ-потребитель индексных событий.
9. Запускаются goroutine-воркеры и начинается обработка обновлений Telegram.

При ошибке догоняющей синхронизации во время старта Go-бот аварийно завершает
запуск через `panic`, чтобы оркестратор перезапустил реплику.

## Поток Модерации

### `/ban`

1. Обновление Telegram преобразуется в `domain.Message`.
2. `moderation.Service` игнорирует личный чат как цель модерации и
   отвечает информационным сообщением.
3. Для команды `/ban` сервис проверяет права администратора через Telegram
   `GetChatMember`.
4. Команда без ответа на сообщение или с ответом на текст не создает блокировку.
5. Для ответа на сообщение с медиа вызывается `ContentBlocker.Block`.
6. `BlockOrchestrator` последовательно вызывает `PrepareBlock` у всех
   сопоставителей. Неподдерживаемый контент не считается ошибкой.
7. Если ни один сопоставитель не поддержал контент, возвращается
   `ErrUnsupportedContent`.
8. В одной PostgreSQL транзакции:
   - создается `media_ban`;
   - каждый подготовленный сопоставитель сохраняет свой артефакт;
   - если ни один артефакт не был создан из-за ограничений уникальности,
     пустой `media_ban` удаляется;
   - создается событие исходящего журнала Watermill `media.ban.created.v1`.
9. После фиксации транзакции Go-бот оптимистично применяет подготовленные
   блокировки к локальным Go-индексам.
10. Бот удаляет целевое сообщение и команду `/ban`.

ИИ-векторный сопоставитель в `/ban` вычисляет векторные представления через
ИИ-сервис `/embed`, но сохраняет `ai_vector_ban` и `ai_vector_frame` в той же
PostgreSQL транзакции Go-бота.

### Проверка входящего медиа

1. Воркер передает сообщение в `moderation.Service`.
2. Для обычного сообщения сервис проверяет само сообщение и сообщение, на
   которое был сделан ответ, если они содержат медиа.
3. `BlockOrchestrator.IsBlocked` вызывает сопоставители по порядку.
4. Первый положительный сопоставитель завершает проверку.
5. При совпадении бот удаляет сообщение через Telegram `deleteMessage`.

## Сопоставители

### Точное Совпадение

- Поддерживает любой контент с непустым `file_unique_id`.
- Исходная таблица: `blocked_exact`.
- Локальный индекс: `map[chat_id,file_unique_id]`.
- Правило дублей: `UNIQUE(chat_id, file_unique_id)`.
- Применение события: `LoadByBanUID` из PostgreSQL и добавление в map.

### Imagehash

- Поддерживает фото и статичный стикер, которые можно скачать.
- Извлекает один кадр через ограниченный декодер изображений.
- Строит варианты `goimagehash` pHash: оригинал и повороты 90/180/270.
- Исходные таблицы: `blocked_image`, `blocked_image_hash`.
- Локальный индекс: линейный поиск по pHash с порогом расстояния Хэмминга.
- Правило дублей: `UNIQUE(chat_id, hash_version, hash_signature)`.
- Дедупликация индекса: сигнатура внутри `LinearIndex`.

### Videolike

- Поддерживает Telegram-анимацию и WebM-видеостикер.
- Использует FFmpeg для извлечения кадров с лимитами количества кадров,
  размеров, длительности и размера файла.
- Для каждого кадра строит pHash.
- Исходные таблицы: `blocked_video_like`,
  `blocked_video_like_frame_hash`.
- Локальный индекс: линейный поиск по хешам кадров.
- Правило совпадения: минимальное число совпавших кадров и минимальная доля
  совпадения.
- Правило дублей: `UNIQUE(chat_id, hash_version, hash_signature)`.
- Дедупликация индекса: сигнатура внутри `LinearIndex`.

### ИИ-Векторный

- Go-сопоставитель поддерживает фото, статичный стикер, WebM-видеостикер и
  анимацию.
- Go-сопоставитель извлекает PNG-кадры и вызывает ИИ-сервис:
  - `/embed` для `/ban`;
  - `/search` для проверки входящего медиа.
- Исходные таблицы: `ai_vector_ban`, `ai_vector_frame`.
- Правило дублей: `UNIQUE(chat_id, model_name, model_revision,
  vector_signature)`.
- Векторы хранятся как float32 `BYTEA`.
- ИИ-сервис держит локальный индекс FAISS HNSW как производную проекцию.

## Схема PostgreSQL

### `media_ban`

Агрегат блокировки. Связывает артефакты всех сопоставителей через `ban_uid`.

Ключевые поля:

- `ban_uid UUID PRIMARY KEY`;
- `chat_id`;
- `media_type`;
- `file_unique_id`;
- `active`;
- `created_at`, `updated_at`, `deactivated_at`.

Индексы:

- `media_ban_chat_active_idx(chat_id, active)`;
- `media_ban_active_created_idx(active, created_at)`.

### Артефакты Сопоставителей

- `blocked_exact` - артефакт exact, первичный ключ `ban_uid`, уникальное
  ограничение
  `(chat_id, file_unique_id)`.
- `blocked_image` - метаданные imagehash-артефакта, уникальное ограничение
  `(chat_id, hash_version, hash_signature)`.
- `blocked_image_hash` - варианты pHash по `image_id`.
- `blocked_video_like` - метаданные video-like-артефакта, уникальное ограничение
  `(chat_id, hash_version, hash_signature)`.
- `blocked_video_like_frame_hash` - pHash кадров по `video_like_id`.
- `ai_vector_ban` - метаданные ИИ-векторного артефакта, признак активности и
  сигнатура векторов.
- `ai_vector_frame` - векторные представления кадров в формате `BYTEA`;
  триггер проверяет размер бинарного значения относительно `vector_dim`.
- `ai_vector_index_state` - сохраненное состояние файла FAISS: модель,
  ревизия, размерность, тип индекса, путь к файлу, хеш активных векторов и
  контрольная сумма файла.

### Исходящие События и Контрольные Точки

- `watermill_outbox_events` - долговременный журнал событий для Watermill
  и догоняющей синхронизации индексов.
- `watermill_offsets_outbox_events` - позиции Watermill SQL-подписчика для
  группы потребителей, публикующей исходящие события.
- `index_checkpoints` - контрольная точка для пары потребитель/индекс:
  `(consumer_id, index_name)`, последняя примененная позиция
  `(transaction_id, offset)`, признак устаревшего индекса и причина.

Обновление контрольной точки монотонное и не двигается назад.

## События

### Тип События

Текущее доменное событие:

- `media.ban.created.v1`.

Полезная нагрузка содержит:

- `ban_uid`;
- `chat_id`;
- `media_type`;
- `file_unique_id`.

### Публикатор Исходящих Событий

`BlockOrchestrator` записывает событие в исходящий журнал Watermill в той же
транзакции, что и артефакты блокировки. `outboxpublisher` читает
`watermill_outbox_events` через Watermill SQL-подписчик и публикует события в
обменник RabbitMQ `bastyle.events`.

Настройки публикатора RabbitMQ:

- устойчивый обменник типа topic;
- включено подтверждение доставки;
- ключ маршрутизации равен типу события;
- AMQP-идентификатор сообщения равен Watermill UUID;
- тип содержимого равен `application/json`.

### Потребители Индексных Событий

Каждая реплика использует собственную устойчивую quorum-очередь:

```text
bastyle.replica.<replica_id>.events
```

Привязки:

- `media.ban.#`;
- `index.#`.

Сообщение RabbitMQ считается сигналом. По сигналу или периодическому тику
потребитель:

1. Читает контрольную точку для каждого локального индекса.
2. Загружает события исходящего журнала PostgreSQL после контрольной точки в
   порядке транзакций.
3. Применяет поддерживаемые события.
4. Обновляет контрольную точку после успешного пакета.
5. Помечает контрольную точку `stale=true`, если применение события завершилось
   ошибкой.

Go-синхронизатор догоняет exact, imagehash и videolike индексы. ИИ-сервис
сопоставления имеет собственный Python-синхронизатор для `ai_vector`.

## Начальная Загрузка и Пересборка

### Go-Индексы

Во время создания сопоставителей Go-индексы строятся из активных блокировок
PostgreSQL. Когда индексные события включены, Go-бот выполняет догоняющую
синхронизацию по исходящему журналу PostgreSQL до запуска RabbitMQ-потребителя
индексных событий.

Если применение события завершилось ошибкой, контрольная точка помечается как
устаревшая. Проверка готовности обнаруживает такие контрольные точки и
возвращает `unavailable` при наличии устаревших индексов.

### ИИ-Индекс FAISS

ИИ-сервис сопоставления использует `FaissHNSWVectorIndex.load_or_rebuild`:

1. Загружает активные ИИ-блокировки из PostgreSQL по модели, ревизии и
   размерности вектора.
2. Загружает сохраненный `ai_vector_index_state`.
3. Если состояние индекса, хеш активных векторов и контрольная сумма файла
   совпадают, загружает файл FAISS.
4. Иначе пересобирает FAISS из активных векторов PostgreSQL и сохраняет новое
   состояние.

Текущее создание ИИ-индекса ленивое по размерности вектора: индекс загружается
или пересобирается при первом поиске, добавлении или применении события для
этой размерности. Строгая ранняя готовность для неизвестных при старте
размерностей остается открытым архитектурным ограничением.

Когда индексные события включены, ИИ-сервис выполняет синхронный bootstrap
catch-up по исходящему журналу PostgreSQL до запуска фонового RabbitMQ consumer.
Ошибка bootstrap прерывает startup сервиса, чтобы оркестратор мог перезапустить
реплику.

### Правило Пересборки

Если локальный индекс поврежден, устарел или его контрольной точке нельзя
доверять, он должен быть пересобран из активных блокировок PostgreSQL. После
успешной пересборки контрольная точка должна соответствовать позиции исходящего
журнала, покрытой использованным снимком данных.

## ИИ-Сопоставитель FastAPI

Python-сервис находится в `services/aimatcher`.

HTTP-эндпоинты:

- `GET /health` - проверяет пул PostgreSQL и, если включено, устаревшие
  контрольные точки ИИ-векторного индекса.
- `POST /embed` - принимает упорядоченные файлы изображений и возвращает
  векторные представления.
- `POST /ban` - устаревший прямой эндпоинт для ИИ-векторной блокировки; сохраняет
  векторы через `PostgresVectorStore` и обновляет FAISS.
- `POST /search` - строит векторные представления для загруженных кадров и ищет
  в FAISS по `chat_id`.

Основные модули:

- `main.py` - настройки, пул БД, модель, сервис векторов, RabbitMQ-потребитель и
  жизненный цикл FastAPI;
- `api.py` - HTTP-контракт и `VectorIndexService`;
- `model.py` - обертка модели Transformers;
- `images.py` - декодер Pillow с лимитом пикселей и изменением размера;
- `storage.py` - PostgreSQL-хранилище векторов;
- `index.py` - индекс FAISS HNSW, контрольная сумма и хеш активных векторов;
- `index_events.py` - чтение исходящего журнала, хранилище контрольных точек,
  применитель ИИ-событий и RabbitMQ-потребитель.

Модель использует Hugging Face Transformers с `trust_remote_code=True`,
зафиксированной `model_revision` и `use_safetensors=True`. Промышленный образ
загружает настроенную ревизию во время сборки.

## Среда Выполнения и Развертывание

### Docker

`infra/docker/Dockerfile.bot`:

- собирает исполняемый файл Go с `CGO_ENABLED=0`;
- образ времени выполнения основан на `debian:bookworm-slim`;
- устанавливает `ca-certificates`, `curl`, `ffmpeg`, `yq`;
- запускается от непривилегированного пользователя `bastyle`;
- использует `/var/lib/bastyle` как рабочую директорию.

`infra/docker/Dockerfile.aimatcher`:

- базовый образ `python:3.12-slim-bookworm`;
- устанавливает Python-зависимости;
- загружает настроенную ревизию модели Hugging Face;
- запускается от непривилегированного пользователя `bastyle`;
- открывает внутренний порт `8080`.

`infra/docker-compose.yaml` сейчас описывает:

- `bastyle-blacklist`;
- `bastyle-aimatcher`;
- `bastyle-rabbitmq`;
- общий том `bastyle-data` для артефактов времени выполнения, например индекса
  FAISS;
- том RabbitMQ.

Сервис PostgreSQL остается запланированным инфраструктурным добавлением для
локального Docker Compose.

### Systemd

`infra/systemd/bastyle-blacklist.service` запускает Go-бота от пользователя
`bastyle_bot`, использует `/var/lib/bastyle`, читает
`/etc/bastyle/config.yaml`, перезапускает процесс при ошибке, ограничивает
память до `512M`, включает `NoNewPrivileges` и `PrivateTmp`.

## Проверки Состояния, Готовность и Метрики

Go-бот:

- `/health` возвращает JSON `ok` или `unavailable`;
- проверяет доступность PostgreSQL;
- когда индексные события включены, проверяет устаревшие контрольные точки для
  локальных применителей индексных событий;
- эндпоинт метрик отдает количество неопубликованных исходящих событий и
  максимальный возраст очереди накопившихся событий в текстовом формате
  Prometheus.

ИИ-сервис сопоставления:

- `/health` проверяет доступность PostgreSQL;
- если ИИ-индексные события включены, проверяет устаревшую контрольную точку
  `ai_vector`;
- доступность модели проверяется неявно при запуске сервиса, потому что модель
  создается в точке сборки приложения.

Открытое архитектурное ограничение: явно разделить проверку жизнеспособности и
проверку готовности, добавить проверку отставания индексов и не направлять
трафик на реплику до завершения начальной догоняющей синхронизации.

## Границы Безопасности

Недоверенные входные данные:

- обновления Telegram и метаданные файлов;
- загруженные файлы Telegram;
- multipart-загрузки FastAPI;
- сообщения RabbitMQ;
- сохраненные в PostgreSQL медиа-метаданные пользовательского происхождения.

Текущие защитные меры:

- Telegram `/ban` требует статус администратора или создателя в целевом чате.
- Загрузка файлов ограничена по размеру.
- Декодирование изображений проверяет размеры и условия распаковочной бомбы.
- Извлечение FFmpeg имеет лимиты кадров, размеров и времени выполнения и
  запускается с
  `-nostdin`.
- Количество файлов и общий размер загрузки в ИИ-сервисе ограничены.
- Пул PostgreSQL использует таймаут подключения и `statement_timeout` для
  каждого соединения.
- HTTP-клиент к ИИ-сервису имеет таймаут запроса.
- Контейнеры бота и ИИ-сервиса запускаются от непривилегированных
  пользователей.
- Внутренний ИИ-сервис сопоставления не должен публиковаться наружу; он
  рассчитан на приватный межсервисный трафик от Go-бота.

Чувствительные к безопасности примечания:

- Токен Telegram, PostgreSQL DSN и RabbitMQ URL являются секретами или могут
  содержать секреты; их нельзя логировать или коммитить с промышленными
  значениями.
- ИИ-модель использует `trust_remote_code=True`; ревизия должна оставаться
  зафиксированной, а обновления модели нужно ревьюить как изменения кода.
- Интерактивная документация FastAPI включена по умолчанию, если ее не
  отключить при развертывании или не закрыть приватной сетевой маршрутизацией.
- Порт управления RabbitMQ в Docker Compose предназначен для локальной
  разработки и не должен публиковаться наружу в промышленном окружении.

## Стратегия Тестирования

Тесты проекта описаны в [tests.md](tests.md). При архитектурном планировании и
перед добавлением новых тестов нужно сверяться с этим документом.

Общие правила:

- Модульные и функциональные тесты Go запускаются через
  `make -C services/bot test`.
- Интеграционные Go-тесты с внешними зависимостями используют
  Docker/testcontainers.
- Тесты ИИ-сопоставителя запускаются через `make -C services/aimatcher test`.
- Тесты по задачам выполняются внутри постоянного Docker runner, а не через
  одноразовые контейнеры только для экономии времени.
